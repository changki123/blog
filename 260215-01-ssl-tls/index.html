TLS와 SSL, 그리고 AWS에서의 활용

2025-02-15
:: tags:  #AWS  #SSL  #TLS  #보안  #인증서

TL;DR

  • SSL과 TLS는 기술적으로 다른 버전이지만, 실무에서는 같은 의미로 사용
  • SSL 3.0 → TLS 1.0 → TLS 1.2/1.3으로 발전
  • AWS에서는 ACM, ALB, CloudFront 등 다양한 서비스에서 TLS 적용

SSL vs TLS: 무엇이 다른가?

역사적 배경

SSL 1.0 (출시 안됨)
  ↓
SSL 2.0 (1995, 넷스케이프)
  ↓
SSL 3.0 (1996, 넷스케이프)
  ↓
TLS 1.0 (1999, IETF) ← 이름 변경!
  ↓
TLS 1.1 (2006)
  ↓
TLS 1.2 (2008)
  ↓
TLS 1.3 (2018)

SSL (Secure Sockets Layer)

  • 넷스케이프(Netscape Communications)가 개발한 암호화 프로토콜
  • 웹 브라우저와 서버 간 안전한 통신을 위해 만들어짐
  • SSL 3.0은 2015년 POODLE 취약점으로 공식 폐기

TLS (Transport Layer Security)

  • IETF(Internet Engineering Task Force)가 SSL 3.0을 기반으로 표준화
  • 넷스케이프 상표권 문제로 이름을 TLS로 변경
  • 현재는 TLS 1.2 이상 사용 권장 (PCI DSS 등 컴플라이언스 요구사항)

왜 아직도 SSL이라고 부를까?

실무에서는 이렇게 말합니다:

  • "SSL 인증서 발급해주세요"
  • "SSL 설정 좀 확인해봐"
  • "HTTPS는 SSL 적용한 거잖아"

하지만 실제로는 TLS 1.2나 1.3을 사용하고 있습니다.

이유는 간단합니다:

  1. SSL이 먼저 유명해져서 용어가 굳어짐
  2. 마케팅 용어로 "SSL 인증서"가 더 친숙함
  3. 검색 키워드도 "SSL"이 더 많이 사용됨

마치 "티슈"라고 하면 브랜드 상관없이 모두 휴지를 가리키는 것처럼, "SSL"은 암호화 통신 전반을 가리키는 일반 명사가 되었습니다.

AWS에서의 TLS 활용

AWS에서는 다양한 서비스에서 TLS를 지원하며, 통합 관리가 가능합니다.

1. ACM (AWS Certificate Manager)

# ACM의 핵심 장점
- 무료 인증서 발급 및 자동 갱신
- AWS 서비스와 완벽한 통합
- 관리 부담 최소화

지원 서비스:

  • Elastic Load Balancer (ALB, NLB, CLB)
  • CloudFront
  • API Gateway
  • Elastic Beanstalk

Let's Encrypt처럼 수동 갱신할 필요 없이, ACM이 자동으로 갱신해줍니다. 다만 외부에서 임포트한 인증서는 수동 관리가 필요하므로 Zabbix 등으로 만료일 모니터링이 중요합니다.

2. Application Load Balancer (ALB)

# ALB TLS 설정 예시
Listeners:
  - Protocol: HTTPS
    Port: 443
    Certificates:
      - CertificateArn: arn:aws:acm:...
    SslPolicy: ELBSecurityPolicy-TLS-1-2-2017-01

주요 기능:

  • TLS 종료(Termination): 클라이언트와의 TLS 연결을 ALB에서 처리
  • SSL Policy: TLS 버전과 암호화 스위트 조합 선택 가능
  • SNI (Server Name Indication): 하나의 ALB에 여러 도메인 인증서 적용

3. CloudFront

엣지 로케이션에서 TLS를 처리하여 전 세계적으로 빠른 HTTPS 서비스를 제공합니다.

사용자 → CloudFront (TLS 종료)
           ↓
         Origin (선택적 재암호화)

구성 옵션:

  • Viewer Protocol Policy: HTTP/HTTPS 리다이렉션 정책
  • Origin Protocol Policy: CloudFront → Origin 간 암호화 여부
  • Custom SSL Certificate: ACM 인증서 연결 (us-east-1 리전 필수)

4. RDS/Aurora

데이터베이스 연결도 TLS로 암호화할 수 있습니다.

-- MySQL/MariaDB에서 SSL 강제
SET GLOBAL require_secure_transport = ON;

# Python에서 RDS SSL 연결
import pymysql

connection = pymysql.connect(
    host='db.example.com',
    user='admin',
    password='password',
    database='mydb',
    ssl={'ca': '/path/to/rds-ca-bundle.pem'}
)

5. API Gateway

REST API나 WebSocket API에 커스텀 도메인 적용 시 TLS 설정이 필요합니다.

# mTLS (Mutual TLS) 지원
- 클라이언트 인증서 검증
- 양방향 인증으로 보안 강화
- IoT 디바이스 인증 등에 활용

실무 아키텍처 패턴

End-to-End 암호화

Client 
  ↓ (TLS 1.3)
CloudFront 
  ↓ (TLS 1.2)
ALB 
  ↓ (TLS 1.2)
EC2/ECS

보안 요구사항이 높은 경우, 모든 구간에서 암호화를 유지합니다.

TLS Offloading

Client 
  ↓ (HTTPS)
ALB 
  ↓ (HTTP - 내부 네트워크)
EC2/ECS

VPC 내부는 암호화하지 않아 백엔드 서버의 CPU 부담을 줄입니다. 대신 네트워크 보안(Security Group, NACL)으로 보호합니다.

모니터링과 관리

Zabbix에서 SSL 인증서 모니터링

# Web Scenario로 인증서 만료일 체크
web.test.error[SSL 인증서 체크]
web.test.time[SSL 인증서 체크,,resp]

ACM 인증서는 자동 갱신되지만, 외부 임포트 인증서나 EC2에 직접 설치한 인증서는 반드시 모니터링해야 합니다.

OpenSSL 명령어로 확인

# TLS 버전 확인
openssl s_client -connect example.com:443 -tls1_2

# 인증서 정보 확인
openssl s_client -connect example.com:443 2>/dev/null | \
  openssl x509 -noout -dates

# 암호화 스위트 확인
nmap --script ssl-enum-ciphers -p 443 example.com

보안 Best Practices

  1. 최신 TLS 버전 사용

    • TLS 1.3 우선 (가능한 경우)
    • 최소 TLS 1.2 이상

  2. 강력한 암호화 스위트

    • Forward Secrecy 지원 (ECDHE)
    • AES-GCM 같은 AEAD 암호화

  3. 인증서 관리

    • 자동 갱신 설정 (ACM 활용)
    • 만료일 모니터링 (수동 관리 인증서)
    • Private Key 보안 관리

  4. HSTS (HTTP Strict Transport Security)

   Strict-Transport-Security: max-age=31536000; includeSubDomains

마치며

실무에서는 "SSL"이라는 용어를 계속 사용하지만, 실제로는 TLS 기술을 사용하고 있다는 점을 이해하는 것이 중요합니다. AWS 환경에서는 ACM과 다양한 서비스의 통합으로 인증서 관리가 매우 편리해졌지만, 외부 인증서나 EC2 직접 설치의 경우 여전히 모니터링과 수동 관리가 필요합니다.

보안은 한 번 설정하고 끝나는 것이 아니라 지속적인 관리와 업데이트가 필요한 영역입니다. TLS 버전 업데이트, 취약한 암호화 스위트 제거, 인증서 만료 관리 등을 체계적으로 관리해야 안전한 서비스를 운영할 수 있습니다.
